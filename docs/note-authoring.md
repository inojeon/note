# 노트 작성 가이드

노트는 `content/notes/<id>/index.md`에 작성한다. 설명에 쓰는 그림·데이터와 선택적인 `preview.md`도 같은 폴더에 둔다. Hugo가 이 묶음을 읽어 `/notes/<id>/` 주소의 HTML을 만든다.

## 새 노트 시작하기

저장소 최상위에서 미리보기를 켠다.

```sh
tools/hugo server -D
```

간단한 실제 예시는 `content/notes/vector/index.md`다. 아래 명령으로 새로운 폴더에 복사할 수도 있다. 이미 있는 폴더 이름은 사용하지 않는다.

```sh
mkdir content/notes/my-concept
cp content/notes/vector/index.md content/notes/my-concept/index.md
```

복사 후 제목·요약·주제·설명·연결 대상을 새 내용에 맞게 바꾼다. 기존 원본 추적용 `legacy_source`는 새 노트에서는 지운다. 복사한 실험 참조는 학습 내용과 맞을 때만 사용한다. 그림을 참조한다면 해당 그림도 새 노트 폴더에 넣는다.

빈 문서로 시작하려면 다음 예시를 `content/notes/my-concept/index.md`에 붙여 넣는다.

```markdown
---
title: "새 개념의 제목"
summary: "이 노트에서 무엇을 이해할 수 있는지 한두 문장으로 씁니다."
params:
  topics: [linear-algebra]
  search_terms: ["영문 이름", "다른 표현"]
  prerequisites:
    - id: vector
      reason: "벡터의 성분과 덧셈을 먼저 알면 예시를 이해하기 쉽습니다."
  related:
    - id: basis
      reason: "같은 대상을 다른 기준으로 표현하는 방법으로 이어집니다."
---

## 어떤 질문에서 시작하나요

먼저 독자가 떠올릴 수 있는 상황을 설명합니다.
필요한 용어는 [벡터](../vector/)처럼 관련 개념으로 연결합니다.

## 작은 예로 확인하기

조건을 정하고 직접 확인할 수 있는 예를 씁니다.

## 적용 조건과 헷갈리기 쉬운 점

설명이 성립하는 조건과 이 예시가 다루지 않는 범위를 밝힙니다.
```

여기서 `my-concept`가 ID다. 소문자 영문·숫자·하이픈을 쓰며 제목을 바꿔도 폴더 이름은 유지한다. 별도 카탈로그에 새 노트를 등록할 필요는 없다.

## 문서 정보의 규칙

파일 처음의 `---` 사이에는 YAML 메타데이터를 쓴다. Hugo의 JSON frontmatter도 지원하지만 새 문서는 아래 YAML 형식을 기본으로 사용한다. 들여쓰기는 공백으로 하고, 콜론이나 특수 문자가 있는 문장은 따옴표로 감싼다.

| 항목 | 내용 |
| --- | --- |
| `title` | 필수. 페이지 제목과 개념 미리보기에 사용한다. |
| `summary` | 필수. 요약, 검색 결과, 연결 카드에 사용한다. |
| `params.topics` | 필수. 등록된 주제 ID를 하나 이상 적는다. |
| `params.search_terms` | 선택. 영문 이름·약어·동의어를 문자열 목록으로 적는다. |
| `params.prerequisites` | 선택. 먼저 읽을 노트의 `id`와 필요한 `reason`을 적는다. |
| `params.related` | 선택. 이어 읽을 노트의 `id`와 연결 이유를 적는다. |

현재 주제는 `linear-algebra`, `quantum-chemistry`, `quantum-computing`, `vqe`, `sqd`, `sqd-workflow`다. 새 주제는 `hugo.toml`의 `[params.topics]`에 ID와 화면 이름을 한 번 등록한다. 새로운 노트를 기존 주제에 추가할 때는 설정을 수정하지 않는다.

선수 개념이 없으면 해당 항목을 생략하거나 `prerequisites: []`로 쓴다. 연결 이유는 대상 노트의 질문을 반복하기보다 **현재 노트를 읽는 데 왜 필요한지** 설명하면 좋다. 없는 노트 ID를 미리 넣지 않는다.

## 본문, 수식, 그림

페이지의 큰 제목은 `title`에서 생성하므로 본문은 `##`부터 시작한다. 질문 → 직관·실험 → 정확한 정의 → 예·주의점 흐름을 권하지만 모든 노트에 같은 섹션 이름을 강제하지 않는다.

수식은 다음 구분자를 사용한다.

```markdown
문장 안의 수식은 \(v=(3,4)^T\)처럼 씁니다.

$$
\|v\|=\sqrt{3^2+4^2}=5
$$
```

수식은 빌드할 때 렌더링된다. 지원하지 않는 명령이나 잘못된 문법은 Hugo 오류로 확인한다. 복잡한 수식에서는 기호의 의미와 적용 조건도 글로 풀어 쓴다.

그림은 해당 노트 폴더에 두고 파일 이름으로 참조한다.

```markdown
![벡터의 가로·세로 성분을 분리한 그림](vector-plane.svg)
```

대체 텍스트에는 그림의 학습 의미를 쓴다. 컴퓨터의 절대 경로나 `/assets/...` 같은 배포 루트 고정 주소를 넣지 않는다. 일반 본문에는 문서 전체 HTML이나 실행 스크립트를 넣지 않는다.

## 개념 링크와 미리보기

```markdown
같은 벡터도 [기저](../basis/)를 바꾸면 좌표가 달라집니다.
```

내부 개념 링크는 제목·요약으로 만든 미리보기 카드와 연결된다. 대상 노트에 `preview.md`가 있으면 짧은 예시·수식도 함께 보여준다. 설명은 대상 개념 한 곳에서 관리한다.

미리보기 예시는 `content/notes/basis/preview.md`처럼 제목이나 frontmatter 없이 작성한다.

```markdown
\(b_1=(1,1)^T\), \(b_2=(0,1)^T\)라면
\((3,4)^T=3b_1+b_2\)입니다. 새 좌표는 \((3,1)^T\)입니다.
```

미리보기는 짧게 유지하고 중첩 미리보기·실험·스크립트를 넣지 않는다. 전체 단어를 자동 연결하지 않으므로 필요한 첫 등장이나 문맥에서 작성자가 링크를 표시한다. 외부 출처는 일반 외부 링크로 작성한다.

정확한 섹션 주소가 필요하면 본문 제목에 안정적인 ID를 줄 수 있다.

```markdown
## 적용 조건 {#conditions}

[벡터의 해당 설명](../vector/#conditions)
```

위 링크의 `conditions`는 실제 대상 노트에 있어야 한다. Hugo는 내부 페이지·자산과 연결한 제목 섹션의 존재를 확인한다. 생성 결과 전체의 링크·앵커는 구조 검사에서도 확인한다. 상세 동작은 [개념 미리보기 가이드](concept-preview.md)를 따른다.

## 실험 삽입하기

```markdown
{{< experiment id="vector-direction" >}}
```

이 ID는 `content/experiments/vector-direction/`을 가리킨다. 실험의 설명·HTML·JavaScript를 노트에 복사하지 않는다. 같은 실험을 여러 노트에서 사용해도 원본은 하나이며, 한 노트에 두 번 삽입해도 상태는 독립적이다.

실험을 새로 만들거나 계산 방식을 바꿀 때는 [실험 작성 가이드](experiment-authoring.md)를 읽는다. 간단한 시작 예시는 `content/experiments/vector-direction/`이다. 실험이 작동하지 않아도 독자가 핵심 결과를 이해할 대체 설명을 작성한다.

## 읽는 순서 만들기

`content/paths/<경로-id>/index.md`에 다음처럼 작성한다.

```markdown
---
title: "벡터와 좌표 읽기"
summary: "벡터를 표현하고 비교하는 세 가지 도구를 익힙니다."
params:
  steps: [vector, basis, inner-product]
---

## 이 순서로 읽어보세요

벡터의 덧셈에서 시작해 좌표와 길이의 의미를 연결합니다.
```

이 목록으로 경로 화면과 각 노트의 이전·다음 이동이 생성된다. 같은 경로에 같은 노트 ID를 두 번 쓰지 않는다. 주제 분류와 학습 경로는 다르므로 노트가 여러 경로에 포함될 수 있다.

## AI와 함께 작성하고 확인하기

AI에게 배울 질문, 현재 아는 내용, 예시와 실험에서 바꾸고 싶은 값을 설명한다. AI는 `content/` 원본을 만들거나 고치고, 사용자는 브라우저에서 읽고 조작하며 수정 요청한다.

작성 후에는 다음을 확인한다.

- 제목·요약만 읽어도 개념과 범위를 알 수 있는가.
- 정의와 예가 정확하고 가정·단위·근사 조건이 드러나는가.
- 링크·미리보기·수식·그림이 실제 브라우저에서 보이는가.
- 실험의 대표 입력과 예상 결과가 일치하고 좁은 화면과 키보드로도 조작되는가.
- 계산 데이터의 출처·조건이 있는가. 예시 값과 실제 계산값을 구별했는가.

마지막으로 `tools/hugo --minify`로 배포용 빌드를 확인한다. 빌드는 `content/`를 수정하지 않는다. 자동 구조·브라우저 검사는 [개발 안내](development.md)의 별도 환경에서 실행한다. 단순 문장 수정 때문에 과학 계산 패키지를 설치할 필요는 없다.
